# 政府预告的 30 分钟降速，却没说降到多少：8/13 一起把三家电信测出来

![一起测 8 月 13 日的移动网络降速](./assets/images/ooni-run-v2.webp){style="border-radius: 10px;box-shadow:1px 1px 0.6rem #00aeff;"}

8 月 13 日周四 14:30 到 15:00，基隆、台北、新北、桃园、新竹市、新竹县、宜兰的移动网络会降速 30 分钟。降速属于「城镇韧性演习」的一部分，三大电信同时执行。官方公告写明语音通话、短信与小区广播照常，视频流、视频通话、移动支付、云端同步等高流量服务受影响。

行政院、NCC 与电信运营商的公告都载明了时段与受影响的服务，速率数字一个都没有出现。中华电信与台湾大哥大的演练公告从头到尾没有提到降到多少，NCC 对外的说明也只写「模拟移动网络使用受限」。那 30 分钟的实际样貌，目前只有三家电信自己知道。

<!-- more -->

## 8 月 13 日要做的三件事

全部时间为台湾时间（UTC+8）。演练时段是 **14:30 到 15:00**。

### 开始之前，8 月 13 日前先完成

安装 [OONI Probe](https://ooni.org/install/){target="_blank"}，App Store、Google Play 与 F-Droid 都可下载，开源免费。这套工具由 OONI 开发，用途是把网络封锁与连接质量变成可验证的公开数据，完整介绍见[什么是 OONI](../../tools/what-is-ooni.md)。首次启动有一段设置流程，当天才安装会来不及。装好后先执行一次，确认能正常完成。

接着设三个闹钟：`14:15`、`14:35`、`15:10`。下午开会时很容易忘记，设闹钟比记忆可靠。

### 一、关闭 Wi-Fi 与 VPN，改用移动数据

固网与 Wi-Fi 在演练中完全不受影响，测量若在 Wi-Fi 上完成，结果等于零。手机常会自动回连办公室或住家的 Wi-Fi，执行前请先确认已切到移动数据。

VPN、Tailscale 这类会改变连接出口的软件也要先关闭。流量绕经 VPN 之后，测量结果只反映 VPN 运营商那段线路，记录下来的 ASN 也会变成对方的，测不到运营商的降速。

测量完成后可在结果页看到网络名称与 ASN（电信运营商的网络编号），确认那笔确实在移动网络上完成，名称为自己的运营商。

!!! warning "先确认你的移动数据额度"

    性能组里的 `ndt` 是吞吐量测试，会尽量用满当下可用的带宽。App 在运行前就会标出预估值，画面上写的是 5 到 200 MB、约 1 分 30 秒，实际落点随连接速度而定。降速前的 14:15 那轮最耗流量，降速中的 14:35 那轮因为带宽被压低，用量小得多。

    非无限流量的人可以只参与 14:35 与 15:10 两轮，仍然有贡献。

### 二、执行「性能」那组测试

开启 App 后点「测试」，选「性能」，勾选要运行的测项，再按下运行。性能组包含 `ndt`（连接速度）与 `dash`（视频流质量）两个测项，正是测量降速所需，Android 与 iOS 都提供。

!!! tip "请不要用 OONI Run 链接"

    直觉会想发一条 [OONI Run v2](../../tools/ooni-run-v2.md) 链接给大家点，本次请避免。OONI Run v2 目前仅支持 Android，iOS 用户无法开启。内建的「性能」测试两个平台皆可使用。

### 三、三个时间点各执行一次

| 台湾时间（UTC+8） | UTC | 用途 |
|---|---|---|
| `14:15` | `06:15` | 降速前的对照点 |
| `14:35` | `06:35` | 降速中 |
| `15:10` | `07:10` | 恢复后 |

三轮都要用同一支手机、同一个号码，每一轮都在移动网络上完成。位置能固定会让数据更好比对，中途需要移动也不影响参与，只要确认没有切回 Wi-Fi 即可。

如果行有余力，8 月 12 日周三 `14:35` 也测一次。多这一笔，隔日同时段的对照会强很多，成本一样是按一下。

!!! note "只赶上一个时间点也有价值"

    看到本文时已经接近或超过 14:30 的人，直接做 14:35 那轮，之后补做 15:10。单一时间点的数据仍可与其他参与者、与隔日同时段互相参照。

!!! note "降速中上传失败属于正常"

    测量结果需要上传，而演练期间带宽已被压低，上传可能延迟或失败。不需要重复执行，OONI Probe 会把结果排入队列，等网络恢复后自动补传。

想多做一点的人，14:35 那轮可另外执行含 Tor 与 Psiphon 的那组测试（英文界面为 Circumvention），能看出降速对规避工具的影响。

## 按下执行之前，该知道的隐私影响

OONI 发布的测量结果全部公开，内容包含所处的 ASN 与时间戳记，不包含个人 IP 地址。

性能组的暴露程度比其他测项高。`ndt` 的测量对端是 [M-Lab](https://www.measurementlab.net/){target="_blank"}，而 M-Lab 的[隐私政策](https://www.measurementlab.net/privacy/){target="_blank"}载明测试数据会对外公开，公开内容包含你的 IP 地址与日期时间，并且以长期研究为由无限期保留，公开数据集里不做匿名化，除非个别行使 GDPR 或 LGPD 的删除权。

执行 `ndt` 等于把当下的对外 IP 地址写进一份公开且永久保存的数据集。M-Lab 不认证用户、不保存个人的测试历史，移动网络的 IP 又多为浮动，实务上很难对应回特定个人。是否留下这笔记录，请自行斟酌。

App 的性能页面本身也附了免责声明，说明测试透过第三方服务器进行，无法保证 IP 地址不被他人收集。只想贡献网站可达性观测、不愿留下 IP 记录的人，可以改运行网页连接测试（`web_connectivity`，英文界面为 Websites），它不经过 M-Lab。

## 中部场已经示范了后果

8 月 10 日 14:30 到 15:00，同样的降速在中部七县市执行过一轮（UTC 时间 `06:30` 到 `07:00`）。演练结束后，我们查询 OONI 的公开数据库，看台湾在该时段留下了什么。

| 测项 | 该时段全台笔数 | 来源网络 |
|---|---|---|
| `ndt`（连接速度） | 1 | `AS131584` 台湾智慧光网，固网 |
| `dash`（视频流质量） | 1 | 同一个固网 ASN |
| `web_connectivity`（网站可达性） | 803 | 几乎全在固网，HiNet 占 593 笔 |

中华电信移动的 `AS17421` 是 0 笔，远传的 `AS9674` 是 0 笔。

唯一那笔速度测量执行在固定光纤上，测量的网络并未降速。中部那 30 分钟等于没有留下任何独立观测，带宽恢复后，那段时间发生过什么已无从查证。北部场是本次演习的最后一场。

## 台湾的 OONI 观测，四成来自 HiNet

中部场的结果反映了台湾 OONI 数据长期的分布。近 30 天全台湾有 658,037 笔 `web_connectivity` 测量，分布在 25 个 ASN：

| 网络 | 近 30 天笔数 | 占比 |
|---|---|---|
| `AS3462` HiNet | 259,987 | 39.5% |
| 三家移动运营商合计 | 23,451 | 3.6% |
| 　└ `AS24158` 台湾大哥大 | 20,481 | |
| 　└ `AS17421` 中华电信移动 | 2,375 | |
| 　└ `AS9674` 远传 | 595 | |

其余六成多也以固网为主，台湾智慧光网、StarVerse、DaDa Broadband 各有数万笔，另有几所大学的校园网络。

真正需要的性能测项，数字更少。近 30 天全台湾只有 1,025 笔 `ndt`，其中中华电信移动 16 笔、远传 4 笔。同期 `web_connectivity` 是 658,037 笔。

要说明台湾的网络环境，目前可引用的数据主要反映家用固定宽带的状况。台湾有超过三千万的移动号码，多数人一天里大半时间透过移动网络上网。

公开的 aggregation API 只提供测量笔数，不提供设备数，所以上表无法排除少数几台设备反复测量的可能。台湾大哥大同时经营移动与固网，中华电信也是，因此单看一笔 `AS24158` 的测量，判断不出它来自手机还是家用调制解调器。

## 为什么三家要一起测

上面那项辨识问题，正好说明为什么要挑这个时段。演练已公告时段与县市范围，在该时段内、在公告范围中，`AS24158`、`AS17421`、`AS9674` 出现的移动端测量有明确的情境可对应，ASN 这时才足以定位到运营商。平常散在各处的测量没有这个条件。

同一时段只消除了「时间」这一个变因。地点、基站负载、手机型号、信号强度全部还在。十支手机散在七个县市，得到的仍是一批条件互异的观测点，结论只能停在粗粒度的判断，例如三家是否都出现可观察的吞吐下降、下降的量级是否接近。任何精确的运营商排名都超出这批数据能支撑的范围。

即使如此，三家同时面对同一道指令、同一个 30 分钟，仍然是难得的对照时机。单独一家测得再密，也只能得到那一家的曲线。

## 30 分钟的数据能用在哪里

**时段与范围明确的降速样本。** 网络降速研究最难的一环，是不知道降速从几点开始、几点结束、涵盖哪里。多数案例由用户先察觉变慢，研究者事后回推，时间边界永远模糊。北部场由政府预告，日期、时段、县市、运营商全部公开，30 分钟的边界明确。已知的部分仅限「政策在什么时间、什么范围生效」，处理强度并不包含在内，因为目标速率没有公布。预告式的断网在其他国家并非首见，例如考试期间的全国性断网，比较少见的是预告式的降速，加上可切分到各家运营商的粒度。

**台湾移动网络的对照基准。** 有了平时与降速中的对照，未来发生非预期的网络劣化时才有基准可比。少了基准，任何一次异常都只能停在「大家觉得变慢」。价值随参与量放大，30 支手机只是零星个案，300 支才具备数据的分量。

**部分验证官方的说法。** 公告称语音、短信、小区广播正常，只有高流量服务受影响。三份公告对受影响范围的描述并不一致，台湾大哥大的公告把 LINE、WhatsApp、M+ 等通讯软件列进会出现连接延迟与不稳定的范围，行政院的版本则是文字传输正常。`ndt` 与 `dash` 只能检查高流量那一侧，语音、短信与小区广播不在这两个测项的能力范围内。能验证的只有界线的其中一边，仍然值得做。公民社会有能力自己验证公共措施的实际效果，本身就是韧性的一部分。

**规避工具是否被波及。** 带宽被压低时，Tor 与 Psiphon 能否建立连接，是社区长期关注的题目，周四的 30 分钟正好是现成的测试场。

解读时须留意 `ndt` 的测量对端是 M-Lab 的服务器，数字里同时包含最后一哩与到 M-Lab 节点的国际线路，两者无法从单笔结果中分离。

## 一起来

安装 [OONI Probe](https://ooni.org/install/){target="_blank"} 并运行一次。设好 `14:15`、`14:35`、`15:10` 三个闹钟。把本文转给住在北部七县市或在当地工作的朋友。特别欢迎中华电信与远传的用户，两家目前的性能测量近乎零。以现在的密度来说，每家电信有 10 支手机参与就已经是数量级的改善。

不在北部七县市的人也可以在同样的时间点测一次。降速范围外的测量构成对照组，能协助分辨哪些变化来自演练、哪些属于当天的一般波动。

测完之后，可在 [OONI Explorer](https://explorer.ooni.org/){target="_blank"} 用自己的 ASN 与时段查到那笔记录。社区会在演练后把三个时段、各家运营商的结果整理成一篇后续文章。有问题或想一起整理结果的人，欢迎到社区的 [Matrix Public Space](https://matrix.to/#/#community:im.anoni.net){target="_blank"} 讨论。

## 延伸：之后如何用 OONI 佐证研究

本次号召针对单一事件，方法本身可以重复使用。OONI 的数据有三个入口，用途各不相同：

- **[OONI Explorer](https://explorer.ooni.org/){target="_blank"}**：网页界面，适合查单笔测量、看某个国家或 ASN 的趋势，无须写程序。
- **Aggregation API**：`https://api.ooni.org/api/v1/aggregation`，免验证免密钥，可依国家、测项、ASN、时间切分做统计。本文所有数字皆由此查得。查询时间一律使用 UTC，台湾时间需减 8 小时。
- **AWS S3 公开数据集**：`ooni-data-eu-fra`，逐笔原始 JSON，适合需要检视测量细节或做大规模分析的研究。原始数据进入 S3 有数小时到一日的延迟，取用方式与 CSV 输出格式写在 [ASN 观测数据撷取与分析](../../community/asn-coverage-howto.md)，社区维护的撷取程序也在该页。

以本次演练为例，查询条件是 `probe_cc=TW`、`test_name=ndt`（或 `dash`）、`since=2026-08-13T06:00:00Z`、`until=2026-08-13T08:00:00Z`，再依 `probe_asn` 切分成 `24158`、`17421`、`9674` 三组。要判断某个问题该用哪个测项，[OONI 测项速查表](../../community/ooni-nettests-map.md)整理了每个测项测量什么、规格状态，以及台湾是否有数据。台湾的 ASN 覆盖现况见 [ASN 自治网络观测数据分析](../../taiwan/ooni-asn-coverage.md)。

**异常（anomaly）不等于封锁。** OONI 的 `anomaly` 只代表测试未照预期完成，成因包含审查、网络不稳、ISP 暂时故障，以及测试程序本身的问题。将 `anomaly` 比率直接视为封锁率会产生假指控。以 `tor` 测项近 30 天的实测为例，加拿大 `21.2%`、瑞士 `22.2%`、新西兰 `41.1%`，皆为没有审查的国家。中段数值属于噪声，只有比率极端高的少数国家与现实相符。

# :material-fingerprint: 什么是 passkey

passkey 是一把存在你设备或密码管理器里的凭证。网站请它签名时，你用指纹、脸或 PIN 同意，它就签。它一般用来登录，站上的用法完全不同：没有登录，没有账号，没有服务器。我们拿它当你数据的钥匙，靠的是下面两种机制。同一把 passkey 两种都能做，创建时[钥匙页](../utils/passkey.md)会列出它能做哪些事。

## 用法一，数据密钥放在 passkey 里

创建 passkey 时，站上会把一把随机生成的数据密钥放进去，之后每一次验证，保管 passkey 的地方都会把它原样交回来。你在任何设备上用这把 passkey 验证一次，数据密钥就回到网页，网页用它解开存在你设备里的密文。规格里这个字段叫 user handle，写作 `user.id`。

`user.id` 是核心字段，规格要求所有保管方式都交回来，我们在 iPhone 配 Bitwarden 与电脑的 Chrome 上验过，其他组合照规格应该一样。[我的准备清单](../utils/checklist.md)、[威胁模型清单](../utils/threat-model.md)的存档、本机文件加密里的收件人簿，都放在这样的一个暂存区里，共用同一份密文。

代价是数据密钥跟着 passkey 存在密码管理器里，安全等于那个管理器的安全：谁能解锁你的密码管理器，谁就拿得到密钥。密码管理器的导出文件、共享的 vault、服务端被入侵加上一组弱的主密码，走的都是同一条路。这跟设备的屏幕锁是同一个等级，对多数人够用，对碰得到你设备又可能要求你解锁的对手不够。威胁模型清单遇到这种对手就不提供存档。

只用清单这类暂存区工具的话，下面这一节可以跳过，直接看「站上存了什么」。

## 用法二，PRF 现场算出密钥

WebAuthn 的 PRF 扩展让 passkey 内部多藏一把秘密，永远不离开验证器。网页每次验证附一段输入，你同意之后，验证器回传固定 32 字节的输出。同一把 passkey 配同一段输入，永远得到同一段输出。passkey 因此变成一台「只在你按指纹时才回答的密钥计算机」。

站上的[本机文件加密](../utils/age.md)拿这段输出去包 age 的 file key。没有 passkey 就算不出密钥，数据就是一堆密文。这跟「验证通过才显示」完全不同，后者是写在网页里的门禁，谁都绕得过。前者是数学。

跟用法一的差别：数据密钥是凭证里的一个字段，密码管理器看得到，导出文件可能也带着。PRF 的秘密只以算出来的结果离开验证器，网页与画面上都看不到原始秘密。密码管理器本身被打开的话，两种用法都守不住。代价是保管方式要另外实现这个扩展，支持面见下面的限制。

## 跟密语差在哪

| | 密语 | passkey |
|---|---|---|
| 要记什么 | 一组六个词以上的密语 | 不用记，指纹或 PIN |
| 强度来源 | 密语本身，scrypt 拖慢猜测 | 验证器里的随机秘密（文件加密）或密码管理器里的数据密钥（暂存区），都猜不了 |
| 跨设备 | 密语跟着人走 | passkey 同步过去就有。不同步的设备，暂存区可以「登录另一台」，文件加密可以贴备援私钥 |
| 能在哪里解 | 任何装了 age 命令行工具的电脑 | 只有 anoni.net 的网页，而且浏览器要支持 |
| 丢了怎么办 | 忘了就永远打不开 | 丢了就永远打不开。文件加密预设搭备援密钥，暂存区靠导出或传到另一台多放一份 |
| Tor Browser | 可以 | 不行，WebAuthn 整个关闭 |

密语模式的文件在任何地方都解得开，passkey 模式的文件绑在这个域名与你的设备上。两种模式输出的都是标准 age 文件，只是收件人不同。

## 限制

passkey 绑在 `anoni.net` 这个 RP ID 上。浏览器只允许在同一个域名使用，镜像站与 onion 地址用不了。Tor Browser 整个关闭 WebAuthn，`security.webauth.webauthn` 在它的默认配置里是 false。这两条两种用法都适用。

以下只影响文件加密。PRF 扩展的支持面到 2026 年 3 月：macOS 15 以上的 Safari 18、Chrome 132、Firefox 139，iOS 18.4 以上，Android 的 Chrome 配 Google 密码管理器，Windows 11 要 2026 年 2 月的更新之后。桌面上 1Password、Bitwarden、Dashlane 的浏览器扩展支持。Firefox Android 与 Windows 10 不支持。浏览器版本够只是一半，保管 passkey 的密码管理器也要支持，两边都对才算得出密钥，[passkey 钥匙](../utils/passkey.md)页「存到哪里」那张表按保管方式列。

iPhone 与 iPad 另有两道限制。Apple 的实现不把 PRF 需要的数据传给 iCloud 钥匙串以外的保管方式，所以在 iOS 上把 passkey 存进第三方密码管理器的 app，创建得起来却算不出密钥，那一把只能用在暂存区。跨设备的流程，也就是在另一台设备上扫 QR code 那条路，同样拿不到 PRF。要在 iPhone 上做文件加密，就在 iPhone 上选 iCloud 钥匙串创建。

passkey 丢了、密码管理器的账号没了、换到不支持 PRF 的环境，用它加密的文件就永远打不开。所以站上的流程预设搭一把 X25519 备援密钥，文件同时加密给 passkey 与它。那一把可以在加密工具上取消，取消之后只有 passkey 开得了。备援密钥放在跟密文不同的地方。

## 站上存了什么

什么都没有。浏览器基于隐私不让网页查询「这个域名有没有 passkey」，任何查询都会跳提示。所以站上连你有没有建过都不知道，钥匙页每次打开都是空的。每一次开锁都要你当场同意。

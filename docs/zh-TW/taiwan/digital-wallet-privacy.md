# :material-wallet-outline: 數位憑證皮夾保護了什麼

數位發展部的數位憑證皮夾 2025 年底進入試營運，超商取貨已經可以用它代替實體證件。官方說明的重點是選擇性揭露（Selective Disclosure），只給驗證需要的欄位，不必把整張證件交出去。公民團體的批評則集中在法制面，至今沒有法律規範保障其中的隱私權與平等近用公共服務。

兩邊的說法都成立，但都沒有回答技術上的具體問題。皮夾的原始碼以 MIT 授權公開在 [`moda-gov-tw/TWDIW-official-app`](https://github.com/moda-gov-tw/TWDIW-official-app){target="_blank"}，所以問題答得出來。本頁把三個問題分開檢查，各自給出結論。

!!! info "本頁的依據與寫作時間"

    技術結論讀自 2026-09 當時的原始碼，官方說法引自 [wallet.gov.tw](https://wallet.gov.tw/){target="_blank"} 的技術介紹頁、常見問題頁與隱私權政策。軟體會改版，引用的行為日後可能不同。

## 三個該分開問的問題

拿實體證件給店員看，隱私上發生三件事，數位版本各自對應不同的技術機制。

1. **發證方的視角**：知不知道你何時何地出示。實體駕照不會回報給監理所，數位版本要看設計
2. **驗證方之間**：能不能串連你。兩家店取得的是不是同一個可辨識的東西
3. **出示的資格**：誰有資格要求你出示。實體世界靠情境判斷，數位世界靠協定

籠統問「皮夾安不安全」得不到有用的答案，三件事分開問才行。

## 發證方看不到你何時何地出示

結論是看不到，這一項做得好。

官方技術介紹頁寫「使用時，無需每次都得透過發行單位連線確認」。原始碼與此一致，出示時皮夾用手上的憑證即時產生可驗證證明（Verifiable Presentation），不回頭連發證方。

撤銷狀態的查詢也做對了。憑證被撤銷或停權時要有機制讓驗證方知道，最直接的做法是驗證方拿憑證編號去問發證方，但那等於每次出示都通知發證方一次。皮夾採用的是狀態清單（status list），`StatusListPrepareTask` 裡的註解寫明最小尺寸：

```java
// prepare initial bit string with 0s (min. size = 16 KB)
encodedList = ZipUtils.gzipCompressThenBase64(newBitString);
```

16 KB 是 131,072 個位元，一份清單涵蓋十三萬張憑證的狀態。驗證方取整份清單回去自己查對應的位元，發證方只知道有人下載了清單，不知道查的是哪一張。撤銷與停權還分成兩份獨立的清單。

隱私權政策的說法也相符：「可驗證憑證之認證或對外提供個人資料，本部均不會接收到任何個人資料」。

## 不同的驗證方能串連你

結論是能，而且這是目前最實質的隱私限制。

選擇性揭露用的格式是 SD-JWT（Selective Disclosure for JSON Web Tokens）。它的做法是把每個欄位加鹽雜湊，出示時只揭開需要的那幾個。所以「你多給了什麼」確實被擋住了。

擋不住的是「這兩次是同一個人」。同一張憑證每次出示，發證方在上面的簽章是同一個。兩家店比對收到的證明，或同一家店比對你兩次造訪，認得出來自同一張憑證。欄位揭露得再少都一樣，因為簽章本身就是識別碼。

國際上處理這件事的做法是批次發行一次性憑證，發證方一次給一疊，每張用過就丟，彼此之間看不出關聯。台灣的實作沒有這一層：

- `CredentialRequestDTO` 只有單一的 `credentialType`、`holderDid`、`holderPublicKey` 與 `nonce`，沒有批次發證用的憑證數量參數
- `CredentialService.generate()` 回傳單一字串而非清單
- 憑證帶 `expirationDate`，走的是有效期模型而非用過即丟

官方技術介紹頁寫「數位憑證皮夾未來也將支援零知識證明（Zero Knowledge Proof）技術」，與原始碼的現況一致。零知識證明是另一條路徑，能在不出示簽章本身的前提下證明條件成立，做到之後可連結性才會消失。

要公允地說，這不是台灣獨有的落後。零知識證明在數位身分皮夾上還沒有成熟的大規模實作，歐盟也還沒把它寫進正式要求。差別在歐盟至少先用批次發行把問題壓下來。

## 誰能要求你出示，皮夾會查但不會擋

結論介於兩者之間，值得完整說明。

OpenID4VP 協定裡，驗證方用 `client_id` 表明身分，而 `client_id` 的形式決定皮夾能做多少驗證。台灣的伺服器端支援四種：

```java
PRE_REGISTERED("pre-registered")
REDIRECT_URI("redirect_uri")
DID("did")
VERIFIER_ATTESTATION("verifier_attestation")
```

實際產生授權請求與 QR Code 的端點都寫死 `DID`，`REDIRECT_URI` 的那一行留在原始碼裡被註解掉。用 `DID` 形式時授權請求必須簽章，驗證方的身分因此可被驗證。這是四種裡偏強的選擇。

皮夾收到請求後會拿驗證方的 DID 去查信任清單。問題出在查完之後怎麼處理。Android 的字串資源：

> 提醒您，您將提供資料的單位尚未列入【信任清單】，建議再次確認是否要『送出資料』

`KxIdentifierManagerImpl.kt` 裡的註解寫得更直白：

> 如果錯誤代碼是4012且是401i，則跳出信任單位警告視窗並且繼續往下走

未列入清單的驗證方會跳警告視窗，使用者可以按下去繼續。皮夾把判斷交還給使用者，隱私權政策的立場也是同一個：「使用者應自行評估是否透過數位憑證皮夾APP的機制將個人資料分享或揭露予第三方」。

還有一個細節。收證與出示兩個時機的檢查強度不同：

| 時機 | 判斷條件 | 實際檢查的事 |
|---|---|---|
| 收到憑證時 | `issStatus['data']['status'] == 1` | 發行方目前的狀態是否有效 |
| 出示憑證時 | `issStatus['error'] != null` | 該 DID 是否為服務所知 |

出示時只確認查得到查不到，沒有再看狀態。清單裡登記過但狀態已非有效的驗證方，出示時不會觸發警告。

## 信任清單的信任錨點在一個中央服務

官方技術介紹頁描述信任清單的儲存方式：

> 我們將信任清單，可信任的憑證發行者列表，記錄在區塊鏈上，讓清單就像被刻在石碑上，無法被任何人偽造或篡改

皮夾實際查詢的方式是對一個中央服務發 HTTP 請求，路徑是 `GET {frontUrl}/api/did/{issDID}`。公開的原始碼裡沒有任何區塊鏈相關的程式碼，Java、Kotlin、Dart 與 Markdown 檔案裡都搜不到。

有兩種解釋而公開資料無法區分。區塊鏈可能是支撐那個中央服務的獨立元件，只是沒有隨這份程式碼開源。也可能該描述對應的是別的東西。不宜據此推論官方說法不實。

對使用者有影響的是另一件事。不論背後是什麼，皮夾信任的是那個中央服務。服務若被攻破或被要求配合，刻在石碑上的性質保護不到使用者，因為使用者的皮夾從來沒有去讀那塊石碑。

## 歐盟用同一套技術，要求不一樣

歐盟的數位身分皮夾（EU Digital Identity Wallet）採用的標準與台灣同一套。差別在 eIDAS 2.0 把幾項隱私性質寫成法律義務，技術設計是為了滿足義務而來。

驗證方（Relying Party）那一端，法規要求「the relying party shall register」，各成員國須提供識別與驗證驗證方的共同機制，註冊後取得存取憑證（Access Certificate），皮夾靠它確認對方身分。同一份文件也寫明註冊不採事前許可，所以歐盟的模型是「要問就得可被識別並先宣告用途」，不含政府核准誰可以問的環節。

超額索取另有明文：

> In a transaction, a wallet solution shall inform the wallet user whenever the wallet-relying party is asking for more information than what they have registered as intended use and the user will have possibility to reject the transaction.

不可連結性寫在第 5a 條，屬性證明不需要識別使用者時，技術框架須支援確保不可連結性的隱私技術，同條並禁止證明提供者取得可用以追蹤、連結或關聯使用者行為的資料。

四項對照：

| 項目 | 歐盟 EUDI | 台灣數位憑證皮夾 |
|---|---|---|
| 驗證方註冊 | 強制，取得存取憑證才能與皮夾互動，不採事前許可 | 查中央信任清單，未列入時警告而使用者可繼續 |
| 可要求的欄位 | 只能要求已登記且宣告用途者，超出時皮夾須告知並讓使用者拒絕 | 未見對應機制 |
| 不可連結性 | 第 5a 條明文要求，實作用批次發行一次性憑證 | 無批次發證，官方寫明零知識證明為未來工作 |
| 發證方不得追蹤 | 第 5a 條明文禁止 | 出示不回連發證方，技術上已達成 |

一項相同、一項較弱、兩項未見對應。

## 技術能做到哪一步，取決於有沒有人要求

歐盟那四項性質的來源是法律。eIDAS 2.0 先寫成義務，實作再往那個方向長。台灣目前沒有對應的法律要求，公民團體的批評正是這一點。

所以問題不在工程能力。批次發行一次性憑證是現成的做法，驗證方登記用途也是寫得出來的機制，歐盟的實作就在公開的程式碼庫裡。差別在有沒有一份文件要求它做到，以及做不到的時候誰能主張權利。

這跟本區其他的在地議題是同一個結構。能力已經建成，限制它的是授權與程序，而不是技術的上限。

## 讀者可以做什麼

### 知道自己在同意什麼

皮夾出示時的警告視窗按下去就過了，那一格是目前唯一由使用者決定的關口。看到「尚未列入信任清單」的提示時，它的意思是對方沒有登記在案。

### 分開想兩件事

「給了哪些欄位」與「被認出是同一個人」是兩回事。選擇性揭露解決前者，後者目前沒有解。需要匿名的場合，數位憑證皮夾不在它的設計目標之內。

### 追蹤法制進度

本頁的技術結論會隨版本改變，真正決定長期走向的是有沒有法律要求。相關的法制動態見 [台灣個資法 2025 修法](./pdpa-2025.md)。

## 本頁的限制

結論全部來自公開的原始碼與官方文件，沒有實測 App 的網路行為。官方常見問題頁說明 App 採用 GuardSquare DexGuard 提供反靜態分析與反動態分析的防護，所以「手機上執行的二進位檔是否等同這份原始碼」沒有被獨立驗證過。原始碼公開與發行檔加固可以同時成立，對想自行查核的人來說兩者意義不同。

中央信任清單服務與區塊鏈的關係也沒有查清楚，公開資料裡找不到說明。
